title: "プロジェクトマネジメントの骨格・マップ"
---

本章では、日々の開発やプロジェクト推進において、状況を正しく把握し適切に手を打つための検討材料とフレームワークを俯瞰する。

これらは単なる教科書的な知識として丸暗記するものではなく、「今何が起きていて、どこに手を打てば手戻りや待ち時間を防げるか」を判断するための骨格（マップ）である。
情報を滑らかに流し、「もったいない」を削りながら、変化に適応して計画を調整・遂行するための全体像を押さえる。

# プロジェクトマネジメントの代表的フレームワーク

プロジェクトマネジメントの世界で広く参照されている代表的な体系として **PMBOK** と **P2M** がある。これらを重厚な規則集として丸呑みするのではなく、エンジニア・ダンドリの観点から「どう捉え、どう活用するか」を整理する。

- **PMBOK（Project Management Body of Knowledge）**
  - **概要**: 米国 PMI（Project Management Institute）が策定した、世界的なプロジェクトマネジメントの知識体系・デファクトスタンダード。
  - **体系の本質**:
    - プロジェクトのライフサイクル（立ち上げ、計画、実行、監視、終結）や、スコープ・スケジュール・品質・リスク・ステークホルダー・コミュニケーションといった多面的な要素を網羅的に体系化している。
    - プロセス重視のアプローチから、価値提供や柔軟な原則重視のアプローチまで、プロジェクトを成功に導くための知見が集約されている。
  - **ダンドリ視点での使い方**:
    - **「網羅的チェックリスト・辞書」として使う**: すべてを最初から厳密に運用するのではなく、ダンドリを考える時に「リスクやステークホルダー、コミュニケーションに見落としがないか」を点検・診断するインデックスとして活用する。
    - **共通言語の獲得**: ビジネス側や社内外のステークホルダーと対話する際の基盤となる用語・概念の共通理解を持つ。
    - **テーラリング（取捨選択）の徹底**: プロジェクトの規模や不確実性に応じて必要な要素だけを抜き出し、形式主義に陥らないように軽量に適用する。

- **P2M（Project & Program Management）**
  - **概要**: 日本（PMAJ）発のプロジェクト＆プログラムマネジメント体系。エンジニアリング産業や大規模プロジェクトの知見を基盤に策定。
  - **プロジェクトとプログラムの階層構造**:
    - **プロジェクト（Project）**: 単一の明確な成果物・目標を有期で達成する活動。
    - **プログラム（Program）**: 複数のプロジェクトを有機的に束ね、全体として組織や事業の「使命（ミッション）の達成」や「長期的な価値創造」を実現する枠組み。
  - **ダンドリ視点での使い方**:
    - **「なぜこの開発をするのか」という上位目的（ミッション）との接続**: 単に与えられた仕様や機能を納品・リリースするだけでなく、「それがプロダクトや事業の価値にどう結びついているか」を意識したダンドリを行う。
    - **他のメンバーの動きとの統合**: プロジェクトの進行状況や成果物の品質・スケジュール・コスト・リスク・ステークホルダー・コミュニケーションなど、他のメンバーの動きと連動させながらダンドリを行う。
    - 特に自社プロダクト開発において、個別の機能改修（プロジェクト）がプロダクト全体のビジョン（プログラム）にどう貢献するかを見失わないための視座を提供する。

- **フレームワークとの健全な付き合い方**:
  - フレームワークに盲従し「チェックリストを埋めること」「書類を作ること」自体が目的化すると、それ自体が巨大な「もったいない（不要な形式作業や会議）」を生み出す。
  - 目的はあくまで「手戻りや待ち時間を未然に防ぎ、スムーズに価値を届けること」。状況に合わせて取捨選択して道具として使いこなす。

# 戦略のカーネル

プロジェクトを推進する際、「計画」を立てる前にまず必要となるのが「戦略」である。戦略不在のままガントチャートやタスクリストを作っても、本質的な障害にぶつかって破綻する。
リチャード・P・ルメルト氏の名著『良い戦略、悪い戦略』で提唱された「戦略のカーネル（核）」は、プロジェクトマネジメントのダンドリを設計する上で非常に有用な思考フレームワークとなる。

- **「戦略のカーネル（核）」を構成する 3 つの要素**:
  1. **診断（Diagnosis）**:
     - 直面している状況の本質、直面する課題・障害を明確に特定・単純化して捉えること。
     - 「何が本当の問題なのか？」「目的達成を阻んでいる最大の障害（ボトルネックや技術的制約）は何か？」を見極める。
     - 単なる症状（例: 「開発が遅れている」）ではなく、根底にある原因（例: 「仕様決定の権限者が不在で、確認待ちが頻発している」）を特定する。
  2. **基本方針（Guiding Policy）**:
     - 診断で明らかになった課題に対処するための包括的なアプローチ・方針。
     - 「何にフォーカスし、何に目を瞑るか」を決める。
     - 例: 遅延する可能性が最も高い外部 API 連携部分に優先的に時間を割いて開発する。
  3. **行動（Coherent Actions）**:
     - 基本方針を実行に移すための具体的で連動したタスク群・リソース配分。
     - それぞれのアクションが互いに補強し合い、同じ目標に向かって整合している状態。
     - 予定通りに状況が動いているか、というモニタリングもセットで行う。
     - 例: 外部 API 連携部分は毎日朝会を行い、問題が大きくなる前に鎮火する。

- **「悪い戦略」の典型パターン（プロジェクトでやりがちな失敗）**:
  - **スローガンや願望の羅列**: 「高品質なシステムを予定通り短期間でリリースする」「みんなで頑張ってやり切る」といった単なる願望や掛け声。課題の診断も方針もない。
  - **重要な課題・痛みの直視の回避**: 誰も触れたがらない仕様の不整合や社外との調整を見て見ぬ振りをして、表面的な進捗表だけを更新する。
  - **トレードオフのない総花主義**: 「すべてのステークホルダーの要望を100%叶える」とし、優先順位をつけずにすべてを抱え込んで空中分解する。
  - **矛盾したアクション**: 方針と矛盾するタスクが並行して走っている（例: 外部 API 連携部分を優先としながら、ずっと他のタスクと掛け持ちにしている）。

- **ダンドリとしての実践**:
  - プロジェクト計画書やタスクリストを作る前に、「診断 → 基本方針 → 行動」という戦略のカーネルを言語化する。
  - 核心的な課題に対する有効な一手を打つことで、後工程で発生する無駄な試行錯誤や大規模な手戻りを事前に潰す。

# 不確実性の種類

広木大地氏『エンジニアリング組織論への招待』が示すように、プロジェクトマネジメントの主たる目的は「不確実性を削減し、情報を作り出すこと」である。
不確実性を放置して開発を進めることこそが、後工程での「仕様のちゃぶ台返し」「設計の全面やり直し」という最大の「もったいない」を引き起こす。
『エンジニアリング組織論への招待』では、エンジニアリングにおける不確実性を以下の **3 つの種類** に分類している。それぞれ性質が異なり、ダンドリとしてのアプローチも異なる。

- **1. 目的不確実性（Why / What の不確実性）**:
  - **内容**:
    - 「何を作るべきか」「誰のために作るのか」「なぜそれを作るのか」「ユーザーにとって本当に価値があるのか」。
    - 要求や仕様の曖昧さ、顧客自身も気づいていない潜在ニーズ、市場や競合環境の変動。
  - **ダンドリによる対処**:
    - ドキュメント上だけで長期間議論しても目的不確実性は減らない。
    - **動くソフトウェア（MVP・プロトタイプ）の早期提供**: 実際に触れるものを見せて使ってもらい、素早くフィードバックを得る。
    - **仮説検証サイクルの小規模化・高頻度化**: 「何が価値か」を検証する実験タスクを早期に回し、机上の空論を避ける。

- **2. 方法不確実性（How の不確実性）**:
  - **内容**:
    - 「どうやって作るか」「技術的に実現可能か」「非機能要件（性能・セキュリティ・拡張性）を満たせるか」。
    - 未知の技術スタック、外部 API 連携の挙動、アーキテクチャの妥当性、データ移行の難易度など、実現手段に関する不確実性。
  - **ダンドリによる対処**:
    - ぶっつけ本番で大規模実装に入ると、後半で技術的破綻が判明して無限大の手戻りになる。
    - **技術検証や「スパイク」の実施**: 未知の要素や難所は、本実装の前にタイムボックス（半日〜1日など）を区切って検証コードを書き、実現可能性を先に確かめる。
    - **段階的な詳細化（Stepwise Refinement）**: 最初から完璧な設計図を描くのではなく、粗いプロトタイプを使って議論しながら徐々に詳細設計へと落とし込む。

- **3. 通信不確実性（Communication / 人と認識の不確実性）**:
  - **内容**:
    - 「自分が意図したことが相手に正しく伝わっているか」「言葉の定義や暗黙の前提にズレがないか」。
    - 人と人、チームとチーム、役割（ビジネスとエンジニア、エンジニア同士）の間で情報が伝達される際に生じるノイズや誤解、情報の非対称性。
  - **ダンドリによる対処**:
    - 「伝えたつもり」「分かっているはず」という思い込みを排除する。
    - **共通言語（ユビキタス言語）の定義**: 用語集の作成や、ドメイン概念の共通化。
    - **根回し**: 随所での頭出しや打診により、反応を伺いつつサプライズを無くす。相手に情報や提案が通りやすいようにしておく。
    - **テキスト（非同期）と対話（同期）の併用**: チケットや設計メモで輪郭を固定しつつ、ペアワークや短いミーティングで認識のギャップを埋める。
    - **短いフィードバックループ**: デイリースタンドアップ、こまめな PR レビュー、スプリントデモなどを通じて、認識のズレが小さいうちに即座に軌道修正する。

- **不確実性を計画に組み込むダンドリ**:
  - 不確実性をすべてゼロにしてから開発を始めることは不可能である。
  - 「3 つの不確実性のうち、今このプロジェクトで最もリスクが高いものはどれか？」を診断し、その不確実性を早期に潰すタスク（ユーザーインタビュー、技術スパイク、ステークホルダーとのコミュニケーション確立）を計画の前半に配置する。

# プロジェクト推進の 4 点セット

木部智之氏『プロジェクトのトラブル解決大全』などで提唱される「プロジェクト推進の 4 点セット」は、プロジェクトをコントロール可能な状態に保つための実践的かつ強力な基本道具である。
これらが揃っていないと、メンバーは暗闇の中で作業することになり、手戻りや待ち時間、迷走が頻発する。

- **1. プロジェクト憲章（プロジェクト計画書）**:
  - **役割**: プロジェクトの存在意義・目的・スコープ・成功基準を定めた最上位の合意文書。インセプションデッキと近い。
  - **含めるべき要点**:
    - **Why（背景・目的）**: なぜ今この取り組みをやるのか。達成しないとどうなるのか。
    - **What（ゴール・成功基準・成果物）**: 何が達成されたら成功（完了）とみなすのか。定量・定性の測定基準。
    - **When & Constraint（スケジュール・制約条件）**: 納期、予算、人員、技術的制約。
  - **ダンドリ視点**:
    - 途中で意見が対立した際や仕様変更の要否を判断する際の「北極星（判断基準）」となる。
    - 50ページの分厚い計画書ではなく、A4で1〜2枚程度にエッセンスが凝縮され、全員がいつでも読み返せる状態が理想。
    - ※ この本の最初の通り、自分がプロジェクトの目的を達成させるぞ、と腹を括るのを忘れずに。

- **2. 体制・ステークホルダー（知りたいこと）**:
  - **役割**: プロジェクトに関わる人々の役割分担と、関係者の利害・関心の把握。
  - **単なる体制図で終わらせないポイント**:
    - **意思決定者（デシジョンメイカー）の特定**: 最終的にGo/No-Goを判断するのは誰か。
    - **RACIマトリクス的な役割分担**: 実行責任者（Responsible）、説明責任者（Accountable）、相談先（Consulted）、報告先（Informed）の整理。
    - **ステークホルダーの「知りたいこと・関心事（関心のツボ）」の把握**:
      - 経営陣: コスト、ROI、リリース時期、事業リスク
      - ユーザー・現場部門: 操作性、業務フローの変更影響、移行手順
      - 開発チーム: 技術的負債の有無、アーキテクチャの妥当性、実現可能性
  - **ダンドリ視点**:
    - 「誰に、どのタイミングで、どの粒度の情報を届ければ合意がスムーズになるか」を事前に設計し、後からの「そんな話は聞いていない」「やり直せ」を未然に防ぐ。

- **3. 課題管理・リスク管理（Issue Management）**:
  - **役割**: プロジェクトの遂行を妨げている問題（ブロッカー）を可視化し、放置を防ぐ仕組み。
  - **リスク（未来の不確実性）と課題（現在顕在化している問題）の違い**:
    - 課題はすでに発生しており、具体的なアクションで解消しなければプロジェクトが止まる。
  - **課題管理表の必須項目**:
    - 課題の内容（事実と影響）、発生日、オーナー（解決責任を持つ単一の担当者）、期日、現在のステータス、具体的なネクストアクション。
  - **ダンドリ視点**:
    - 課題が「Slackの流れるチャット」や「誰かの頭の中」に埋もれると、期限直前に爆発する。
    - オーナーを必ず1名に定め、定期的に解消状況をトラッキングして課題の滞留をなくし、首尾よく解消して道筋をつける。

- **4. 進捗確認と共有（通信路 / Communication Channel）**:
  - **役割**: プロジェクトの現実の状況（ファクト）を定期的に吸い上げ、必要な関係者に説明責任を果たすパイプライン。
  - **通信路の設計**:
    - 会議体（デイリー、週次定例、月次ステアリングコミッティなど）の目的と参加者の明確化。
    - 非同期の共有手段（Slackチャンネル、ダッシュボード、週報ドキュメント）の活用。
  - **ダンドリ視点**:
    - 「順調です（実は問題があるが言い出しにくい）」という形骸化した報告会を排除する。
    - 悪いニュースや遅延の兆候、ブロッカーが即座に共有され、早期に助け合える心理的安全性と仕組みを担保する。小さいうちであれば新しいダンドリを作りやすい。
    - コミュニケーションの「通信路」を太く短く保ち、情報の伝達遅延という「もったいない」を極小化する。

# 荒ぶる四天王

アジャイル開発のバイブル『アジャイルサムライ』（ジョナサン・ラスマセン著）で紹介される「荒ぶる四天王」は、あらゆるプロジェクトが直面する 4 つの制約パラメータである。
これらは互いに強く影響し合っており、どれかひとつを動かせば他の要素に必ず影響が及ぶ（トレードオフ）。

- **四天王の構成要素**:
  1. **スコープ（Scope / 機能・やるべきことの量）**
  2. **時間（Time / 納期・スケジュール）**
  3. **予算（Budget / コスト・人員・リソース）**
  4. **品質（Quality / 信頼性・テスト網羅度・性能・設計の美しさ）**

- **プロジェクトにおける現実と鉄則**:
  - **「全部固定」は幻想**: スコープも納期も予算も品質もすべて固定して「完璧にやれ」と要求することは、戦略の基本方針で決めたことに反する。無理を通そうとすれば、炎上、残業、品質偽装、あるいはデスマーチに陥る。
  - **「品質」は決して削ってはいけない（禁断の果実）**:
    - 追い詰められたチームが最も安易に手を出しがちなのが「テストを端折る」「リファクタリングを後回しにする」「場当たり的な修正をする」という品質の妥協である。
    - 短期的には進んだように見えても、後工程でバグが雪だるま式に多発し、手戻りと修正に何倍もの時間が奪われ、結果として納期も破綻する（品質負債の複利効果）。
    - 定めた品質が過剰でない限り、削ることは実際にはできない。
  - **「時間」と「予算（人）」は急には動かせない**:
    - 納期はビジネス上の約束（展示会、法改正、資金調達など）で固定されていることが多い。
    - 人員を追加しても、ブルックスの法則（「遅れているソフトウェアプロジェクトへの要員追加は、プロジェクトをさらに遅らせる」）が働き、キャッチアップやコミュニケーションコストで一人当たりの生産性は落ちる。
  - **最も健全な調整弁は「スコープ（機能の引き算）」である**:
    - 納期やリソースが限られている場合、唯一コントロール可能な変数は「何を作り、何をあえて作らないか（スコープ）」である。
    - 要求のそれぞれに優先度をつけて優先度の高い内容から実施し、最初のリリースまでの時間を短縮する。目的不確実性への対処と相性が良い。

- **トレードオフ・スライダーによる合意**:
  - プロジェクト開始時に、ステークホルダーで 4 つの要素（および追加の要素）の優先順位（1位〜4位）を合意しておく。
  - 「何が起きても納期が最優先（時間は固定）なので、問題が起きたらスコープを削る」「今回はスコープが最優先なので、リリース日は柔軟に延ばす」といった意思決定の基準を決めるというダンドリをしておくことで、調整コストと判断待ち時間を激減させる。

# 見積もり（Estimation）

見積もりは、プロジェクトマネジメントにおいて最も誤解されやすく、またトラブルの火種になりやすい領域である。
エンジニアがダンドリを行う上で、見積もりの本質を正しく理解しておくことは極めて重要となる。

- **見積もりの本質: 約束ではなく「確率的予測」である**:
  - 見積もりは「期日を誓うコミットメント（契約・約束）」ではなく、現時点で得られている情報に基づいた「確率的な幅を持った予測」である。
  - 不確実性の高い初期段階ほど見積もりのブレ幅は大きく（不確実性のコーン）、プロジェクトが進んで情報が増えるにつれて収束していく。
  - 人のスキルによって異なり、また、人の慎重さによっても代わる。

- **ソフトウェア開発において最悪ケースは無限大（∞）になりうる**:
  - 工場での生産ラインなどの物理世界と異なり、ソフトウェア開発は知識創造作業であり、目に見えない論理の塊を扱う。
  - 未知の不具合、採用したサードパーティ製ライブラリのバグ、非機能要件（パフォーマンス・セキュリティ）の破綻、基盤アーキテクチャの前提崩壊などが起きると、工数は「2倍」程度ではなく、解決策が見つかるまで実質的に上限は「無限大（プロジェクト停止）」になりうる。
  - したがって、「一点見積もり（『3日で作れます』）」は本質的に嘘を含んでおり、最悪ケースの跳ね上がりを意識した予防策が必要になる。

- **見積もりを成立させるための 2 つの前提**:
  1. **対象のプロセスを自分自身で理解していること・ダンドリを考えられること**:
     - 単に「コードを書く時間」だけでなく、要件の確認、設計、テストコード作成、PRレビュー、CI環境での動作確認、QA、デプロイ、データ移行など、完了までに必要なすべての工程（Doneの定義）が頭に入っていること。
  2. **タスクを自分自身で理解していること・ダンドリを考えられること**:
     - 何をインプットとし、何をアウトプットとするのか、タスクの境界線と完了条件が明確になっていること。何が「分かっていて（既知）」、何が「分かっていない（未知）」かが分離できていること。

- **ダンドリとしての実践的な見積もり・不確実性削減テクニック**:
  - **タスクの細分化（小さく割る）**:
    - 3日以上の大きなタスクは、そのままでは見積もれない（不確実性が高すぎる）。
    - 数時間〜最大でも1日程度で終わる粒度まで分解することで、見落としていた隠れタスクや依存関係が浮き彫りになり、見積もり精度が跳ね上がる。
  - **スパイク（調査・実験用タイムボックス）**:
    - 未知の技術や仕様不明な外部連携は、見積もりを出す前に「半日だけ実験コードを書いて調べる」スパイクタスクを設け、不確実性を先に潰してから本見積もりを行う。
  - **隠しバッファの罠と全体バッファ（CCPM視点）**:
    - 個々のタスクに見積もり担当者がこっそり安全係数（バッファ）を上乗せすると、パーキンソンの法則（与えられた時間いっぱいまで作業を使ってしまう）や学生症候群（期限直前まで着手しない）が働き、バッファはすべて使い果たされて遅延する。
    - 個々の見積もりは「50%の確率で終わる挑戦的な期間」とし、安全余裕はプロジェクト全体の末尾に「プロジェクトバッファ」としてまとめて管理する（詳細は第6章で詳述）。

# ボトルネック

どれほど精緻な計画を立て、個々のメンバーが全力で作業していても、プロジェクト全体のスループット（成果の創出速度）が劇的に落ちることがある。その原因の多くは「ボトルネック（制約条件）」の無視にある。

- **TOC（Theory of Constraints / 制約理論）の基本原則**:
  - ゴールドラット博士が提唱した生産管理の理論。
  - **「システム全体のパフォーマンスは、最も能力の低い工程（ボトルネック）によってのみ決まる」**。
  - ボトルネック以外の部分（非ボトルネック）をいくら効率化・高速化しても、全体のリードタイムは短縮されない。
  - むしろ、非ボトルネックが過剰に作業を進めると、ボトルネックの前に入り切らない仕掛品（WIP / 仕掛かりタスク・レビュー待ちPR）が山積みになり、コンテキストスイッチの増加や手戻りの増大といった巨大な「もったいない」が発生する。

- **開発現場で頻発する典型的なボトルネック**:
  - **コードレビューの滞留**: エンジニアは次々にコードを書くが、テックリードや特定シニアのレビュー待ちでPRが何日も放置される。
  - **仕様・要件の判断待ち**: 開発中に疑問が出ても、PdMや顧客からの返答が来ず、作業がストップして別のタスクに浮気する（マルチタスクの罠）。
  - **リリース・QA環境の制約**: デプロイ環境が1つしかなく、他チームの検証が終わるまでリリースできない。
  - **デプロイ・移行作業の属人化**: 特定のインフラ担当者しか本番反映の手順を知らない。

- **ボトルネックに対処するダンドリの定石（第 6 章への布石）**:
  - **1. ボトルネックを見つける**: 最もタスクが滞留（山積み）している工程を探す。
  - **2. ボトルネックに集中する**: ボトルネックとなっている人や工程に、無駄な作業（雑用、会議、やり直し）をさせない。最も価値の高い作業だけに集中させる。
  - **3. 他のすべてをボトルネックに従属させる**: ボトルネックの処理能力を超えてタスクを着手しない（WIP制限）。前工程が作りすぎない。
  - **4. ボトルネックへの対処の能力を強化する**: ペアプロ・モブプロによるレビューの分散・フロー向上、CI/CDの自動化、テストの自動化、権限委譲による判断の分散。

# まとめ

本章で取り上げた概念やフレームワークは、それぞれが孤立した理論ではない。
すべては**「不確実性に対処し、ボトルネックを見極め、『もったいない』を先回りして潰す」**という思想で貫かれている。

- **戦略のカーネル**で課題を診断し、筋の良い基本方針と首尾一貫した行動を定める。
- **不確実性の種類**を見極め、環境の不確実性は動くもので素早く試し、通信の不確実性は共通言語と短いフィードバックで解消する。
- **4 点セット**によって、目的・体制・課題・通信路というプロジェクトの土台を常に可視化しておく。
- **荒ぶる四天王**のトレードオフを認識し、スコープの引き算で現実的な調整を行う。
- **見積もり**を確率的予測と捉え、タスクを小さく割って不確実性を減らしながら進める。
- **ボトルネック**を常に意識し、全体の流れ（フロー）を阻害している箇所に集中して手を打つ。
