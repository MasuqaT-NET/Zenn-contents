# 自律的に動くチームを目指して

プロジェクトマネジメントの本質は、マネージャーの管理業務をエンジニアに肩代わりさせることではありません。

**「特定のリーダーや PjM がいないと何も動かない構造」を解消すること**です。

専任 PjM にすべての調整や判断を委ねる体制は、PjM の過負荷や判断待ちを招きやすいです。現場のエンジニア一人ひとりがダンドリの視点を持ち、自立して動くことで、チームの開発速度と対応力は向上します。

- 要件の背景を理解し、無駄な実装による手戻りを防ぐ
- 事実・仮説・懸念を整理して意思決定を支援する
- ボトルネックを把握し、PR の分割やレビュー支援を自発的に行う

これらは特別な役職を必要とせず、現場のエンジニアが日々の業務の中で発揮できる技術です。全員がダンドリを担うことで、特定個人のボトルネック化を防ぎ、自律して前進するチームが成立します。

# 本書の要点整理

日々の開発で判断に迷ったときは、次の 4 原則に立ち返ってみてください。

1. **作業時間ではなくリードタイムを縮める**
   実装速度以上に、待ち時間、依存関係による停止、WIP の過大化を減らすことがリードタイム短縮に直結します。
2. **不確実性を早く小さく検証する**
   未知の要件や技術的難所は後回しにせず、モックやスパイクで早期に白黒をつけます。戻りにくい決定（One-way door）ほど先行して小さく検証します。
3. **ボトルネックを見極め、チーム全体で合わせる**
   個人の作業完了にとらわれず、全体の流れを止めているボトルネックを支援してスループットを最大化します。
4. **提案は「相手の不安を減らす形」で届ける**
   相手の評価指標への翻訳、事実・仮説・懸念の切り分け、小さな検証（PoC）、撤退基準の提示が鍵になります。

# 明日からの実践ステップ

| 課題 | 最初のアクション |
| :--- | :--- |
| レビュー待ちが長い | PR を関心事ごとに分割し、動作確認ログやスクショを添えます |
| 仕様や技術に不安がある | 本実装の前に「半日のスパイク（検証タスク）」で成立性を確認します |
| 設計経緯が埋もれる | Issue やチケットに「決定事項」「代替案」「選定理由」を 3 行でメモします |

「読み・書き・プログラミング」に並ぶ基礎技術としての「ダンドリ」。日々の小さな工夫の積み重ねが、開発者自身の働きやすさを作り、チームの生産性を底上げします。

# 参考書籍・知識体系

本書の論理構造は、以下の知見に基づき実務向けに再構成しました。

- リチャード・P・ルメルト『良い戦略、悪い戦略』（日本経済新聞出版）
  - 診断、基本方針、首尾一貫した行動からなる「戦略のカーネル」の思考体系
- 広木大地『エンジニアリング組織論への招待』（技術評論社）
  - 不確実性を「目的・方法・通信」に分解し、情報と意思決定を扱うアーキテクチャ
- エリヤフ・ゴールドラット『ザ・ゴール』（ダイヤモンド社）
  - 全体最適を実現する制約理論（TOC）およびボトルネック管理の原則
- ジョナサン・ラスマセン『アジャイルサムライ』（オーム社）
  - スコープ、時間、リソース、品質のトレードオフ管理とチーム運営
- 木部智之『プロジェクトのトラブル解決大全』（クロスメディア・パブリッシング）
  - 現場の課題とリスクを構造的に可視化・分類する道具立て
- PjMI『PjMBOK ガイド』および PjMAJ『P2M（プロジェクト＆プログラムマネジメント標準ガイドブック）』
  - プロジェクトマネジメントの国際的・標準的知識体系
