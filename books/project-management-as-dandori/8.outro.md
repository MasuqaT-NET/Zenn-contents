# 自律分散型チームへの移行

本書で論じてきたプロジェクトマネジメントの目的は、マネージャーの管理業務をエンジニアに肩代わりさせることではない。

目指すべき状態は、**「特定のリーダーや専任 PM がすべての情報伝達・調整・判断を担わなければ進行しない構造（単一障害点）」を解消すること**である。

専任 PM にすべての意思決定を集約する体制は、短期的には効率的に見えても、PM の過負荷や判断待ちによる現場の待機時間を恒常化させる。一方で、現場のエンジニア一人ひとりがダンドリの観点を持ち、自律的に動くことができれば、チームのデリバリー速度と堅牢性は飛躍的に向上する。

- 課題の背景を把握し、要件を満たさない不要な実装を未然に防ぐ
- 判断に必要な事実・仮説・懸念を整理し、関係者の意思決定コストを下げる
- ボトルネック工程を把握し、PR の分割やレビュー支援を自発的に行う

これらは特別な役職を必要とせず、現場のエンジニアが日々の業務の中で発揮できる技術である。全員がダンドリを担うことで、専任管理者のボトルネック化を防ぎ、自律的に前進し続けるチームが成立する。

# 本書の要点整理

日々の開発において判断に迷った際は、以下の原則に立ち返ることを推奨する。

1. **作業時間ではなくリードタイムを最適化する**
   実装速度の向上以上に、工程間の待機時間、依存関係による停止、過大な仕掛かり作業（WIP）を削減することが、全体のデリバリー速度向上に直結する。
2. **不確実性を早期かつ最小コストで縮小する**
   未知の要件や技術的難所は後回しにせず、モックアップやスパイクを用いて初期に白黒をつける。不可逆な決定（One-way door）ほど、先行して小さな検証を行う。
3. **ボトルネックを特定し、チーム全体で従属させる**
   部分最適（個人の作業完了）にとらわれず、システム全体の流量を制限しているボトルネック工程を支援し、スループットを最大化する。
4. **提案は「相手の不確実性を下げる形」で設計する**
   改善提案を通すためには、相手の評価指標への翻訳、事実と仮説の峻別、限定的な試行（PoC）、撤退基準の明示を行う。

# 明日からの実践ステップ

本書の手法を現場に適用する際は、以下の小さな試行から着手することを推奨する。

- **レビュー待ちが長い場合**：PR を関心事ごとに分割し、動作確認ログやスクリーンショットを添付してレビュワーの負荷を軽減する。
- **仕様や技術に不安がある場合**：数日かけて本実装に着手する前に、「半日間のスパイク（技術検証）」をタスクとして設定し、成立性を確認する。
- **設計判断が属人化している場合**：Issue やチケットに「決定事項」「検討した代替案」「選定理由」を 3 行で記録（ADR 化）する。

「読み・書き・プログラミング」に並ぶ、ソフトウェアエンジニアの基礎技術としての「ダンドリ」。日々の小さな整流化の積み重ねが、開発者自身の作業環境を改善し、チーム全体の生産性を底上げしていく。

# 参考書籍・知識体系

本書の論理構造は、以下の書籍および知識体系の知見に基づき、ソフトウェア開発の実務現場向けに再構成したものである。

- リチャード・P・ルメルト『良い戦略、悪い戦略』（日本経済新聞出版）
  - 診断、基本方針、首尾一貫した行動からなる「戦略のカーネル」の思考体系。
- 広木大地『エンジニアリング組織論への招待』（技術評論社）
  - 不確実性を「目的・方法・通信」に分解し、情報と意思決定を扱うアーキテクチャ。
- エリヤフ・ゴールドラット『ザ・ゴール』（ダイヤモンド社）
  - 全体最適を実現する制約理論（TOC）およびボトルネック管理の原則。
- ジョナサン・ラスマセン『アジャイルサムライ』（オーム社）
  - スコープ、時間、リソース、品質のトレードオフ管理とチーム運営。
- 木部智之『プロジェクトのトラブル解決大全』（クロスメディア・パブリッシング）
  - 現場の課題とリスクを構造的に可視化・分類する道具立て。
- PMI『PMBOK ガイド』／ PMAJ『P2M（プロジェクト＆プログラムマネジメント標準ガイドブック）』
  - プロジェクトマネジメントの国際的・標準的知識体系。
