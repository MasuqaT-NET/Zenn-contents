# 「誰かが指示しないと動けないチーム」を卒業する

本書を通じて伝えたかったのは、プロジェクトマネージャーの退屈な事務作業をエンジニアに押し付けることではない。

本当に目指したいのは、**「特定のリーダーや PM がすべてを把握し、指示し、調整しなければ 1 歩も前に進まない状態」をチームからなくすこと**だ。

専任の PM に頼り切る体制は、一見楽に見えて、実はチーム全員を不幸にする。PM はすべての判断を抱え込んでパンクし、エンジニアは「言われたチケットを消化するだけ」の受け身になり、ちょっとした仕様確認でも何日も手が止まる。

だが、チームのエンジニア一人ひとりがダンドリを身につけていればどうだろうか。

- 課題の背景を確かめて、不要な機能の作り込みを事前に止める
- 判断に必要な情報（事実・仮説・懸念）を揃えて、関係者が即断できるように助ける
- レビューが詰まりそうなら PR を小さく割り、ボトルネックを自発的に助けにいく

これらはすべて、特別な役職につかなくても、現場のエンジニアが今日から発揮できるダンドリの力だ。全員が段取りよく動けるようになれば、チームのボトルネックだった「専任の管理者」はそもそも必要なくなる。

# 本書で手に入れた3つの武器

本書を通じて、あなたには 3 つの武器が手に入ったはずだ。

1. **「もったいない」をなくす視点**
   開発を遅らせているのは作業時間ではなく、待ち時間、手戻り、情報探索などの「もったいない」だ。妥当な作業時間をゼロにはできなくても、無駄なロスを削ぎ落とすだけでチームは驚くほど速くなる。
2. **自分のアイデアを形にする技術**
   ダンドリとは「人に何かを受け入れてもらう技法」でもある。相手の不安（不確実性）を先回りして小さく潰し、低リスクで試せる形で提案すれば、あなたのやりたいカイゼンや挑戦はチームを巻き込んでスルッと通るようになる。
3. **本当のダンドリの勘所**
   ダンドリとは、重たい書類を作ることではない。「後で起きる巨大な損失を、今ちょっとした工夫で安く防ぐ投資」だ。

# 明日からの「小さな一手」

CSV 出力機能の例でも見てきたように、最初の一歩は分厚い計画書を書くことではない。

明日、あなたの現場で最近起きた「待ち時間」「もったいない手戻り」「情報の迷子」の中から、1 つだけ選んで試してみてほしい。

- **PR の放置が気になるなら**：PR を関心ごとに半分に分割し、動作確認の証跡を添えて出してみる。
- **仕様の不安があるなら**：「半日だけ調査のスパイク（技術検証）の時間をください」とチームに相談してみる。
- **重要な決定が流れてしまいそうなら**：Issue やチケットの概要欄に「決定事項とその理由」を 3 行でメモしてみる。

効果があればチームの当たり前にし、微妙なら別のやり方を試せばいい。

「読み・書き・プログラミング」に並ぶ、エンジニアの一生モノの基礎リテラシーとしての「ダンドリ」。
日々の小さな段取りの積み重ねが、あなた自身を自由にし、チームをどこまでも前進させていくはずだ。

# 参考書籍・知識体系

本書の考え方は、以下の優れた書籍や体系の知見を、ソフトウェア開発の実務現場向けに応用・再構成したものである。深く学びたい方はぜひ原著を手に取ってほしい。

- リチャード・P・ルメルト『良い戦略、悪い戦略』（日本経済新聞出版）
  - 診断、基本方針、首尾一貫した行動からなる「戦略のカーネル」の思考法。
- 広木大地『エンジニアリング組織論への招待』（技術評論社）
  - 不確実性を「目的・方法・通信」に分解し、情報と意思決定を扱うアーキテクチャ。
- エリヤフ・ゴールドラット『ザ・ゴール』（ダイヤモンド社）
  - 全体最適を実現する制約理論（TOC）とボトルネックの原則。
- ジョナサン・ラスマセン『アジャイルサムライ』（オーム社）
  - スコープ、時間、予算、品質のトレードオフ（荒ぶる四天王）とチームの動かし方。
- 木部智之『プロジェクトのトラブル解決大全』（クロスメディア・パブリッシング）
  - 現場の状況を正しく把握し、課題とリスクを構造的に可視化する道具立て。
- PMI『PMBOK ガイド』／ PMAJ『P2M（プロジェクト＆プログラムマネジメント標準ガイドブック）』
  - プロジェクトマネジメントの国際的標準知識体系。
