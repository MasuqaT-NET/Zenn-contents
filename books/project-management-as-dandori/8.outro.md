# 「誰かが指示しないと動けないチーム」を卒業する

本書を通じて伝えたかったのは、プロジェクトマネージャーの退屈な事務作業をエンジニアに肩代わりさせることではありません。

本当に目指したいのは、**「特定のリーダーや PM がすべてを把握し、指示し、調整しなければ 1 歩も前に進まない状態」をチームからなくすこと**です。

専任の PM に頼り切る体制は、一見楽に見えて、実はチーム全員を窮屈にしてしまいます。PM はすべての判断を抱え込んでパンクし、エンジニアは「言われたチケットをこなすだけ」の受け身になり、ちょっとした確認でも何日も手が止まってしまいます。

ですが、現場のエンジニア一人ひとりがダンドリを意識できれば、チームの動きは大きく変わります。

- 課題の背景を確かめて、不要な作り込みを未然に防ぐ
- 判断に必要な情報（事実・仮説・懸念）を揃えて、関係者が即断できるように助ける
- レビューが詰まりそうなら PR を小さく割り、チームのボトルネックを自発的に助けにいく

これらはすべて、特別な肩書がなくても、現場のエンジニアが今日から発揮できるダンドリの力です。全員が段取りよく動けるようになれば、ボトルネックになりがちだった「専任の管理者」に頼らなくても、チームは自律して前に進めるようになります。

# 本書で伝えたかったこと

日々の開発で迷ったときは、次の 3 つを思い出してみてください。

1. **「もったいない」を減らす**
   開発を遅らせている最大の要因は作業時間ではなく、待ち時間、手戻り、情報探索などの「もったいないロス」です。無駄なロスを削ぎ落とすだけで、仕事のスピードは自然と上がります。
2. **提案は「相手の不安を潰す」ことから始める**
   ダンドリとは「人に何かを受け入れてもらう技術」でもあります。相手の関心事に言葉を合わせ、小さな試行から始めることで、自分のやりたい改善や挑戦を気持ちよく受け入れてもらえるようになります。
3. **ダンドリは「未来の損失を安く防ぐ投資」**
   ダンドリとは、分厚い計画書を作ることではありません。「後で起きる大きな手戻りを、今ちょっとした確認で防ぐ」ための身軽な工夫です。

# 明日からの「小さな一歩」

CSV 出力機能の例でも見てきたように、最初の一歩は分厚い計画書を書くことではありません。

明日、あなたの現場で最近起きた「待ち時間」「もったいない手戻り」「情報の迷子」の中から、1 つだけ選んで試してみてください。

- **PR の放置が気になるなら**：PR を関心ごとに半分に分割し、動作確認の証跡を添えて出してみる。
- **仕様に不安があるなら**：「半日だけ調査の検証枠をください」とチームに相談してみる。
- **重要な決定が流れてしまいそうなら**：チケットの概要欄に「決定事項とその理由」を 3 行でメモしてみる。

効果があればチームの習慣にし、微妙なら別のやり方を試せば十分です。

「読み・書き・そろばん（技術）」に並ぶ、エンジニアの一生モノのリテラシーとしての「ダンドリ」。
日々の小さな工夫の積み重ねが、あなた自身のストレスを減らし、チームを軽やかに前進させていくはずです。

# 参考書籍・知識体系

本書の考え方は、以下の優れた書籍や知識体系の知見を、ソフトウェア開発の実務現場向けに応用・再構成したものです。深く学びたい方はぜひ原著を手に取ってみてください。

- リチャード・P・ルメルト『良い戦略、悪い戦略』（日本経済新聞出版）
  - 診断、基本方針、首尾一貫した行動からなる戦略の思考法。
- 広木大地『エンジニアリング組織論への招待』（技術評論社）
  - 不確実性を「目的・方法・通信」に分解し、情報と意思決定を扱う視点。
- エリヤフ・ゴールドラット『ザ・ゴール』（ダイヤモンド社）
  - 全体最適を実現する制約理論（TOC）とボトルネックの原則。
- ジョナサン・ラスマセン『アジャイルサムライ』（オーム社）
  - スコープ、時間、予算、品質のトレードオフとチーム運営。
- 木部智之『プロジェクトのトラブル解決大全』（クロスメディア・パブリッシング）
  - 現場の状況を正しく把握し、課題とリスクを構造的に可視化する道具立て。
- PMI『PMBOK ガイド』／ PMAJ『P2M（プロジェクト＆プログラムマネジメント標準ガイドブック）』
  - プロジェクトマネジメントの標準的知識体系。
