# 自律的に動くチームを目指して

本書で伝えたかったプロジェクトマネジメントの本質は、マネージャーの管理業務をエンジニアに押し付けることではない。

目指したいのは、**「特定のリーダーや PM がいないと何も動かない状態」からチームを解き放つこと**だ。

専任 PM にすべての調整や判断を頼り切る体制は、最初のうちは楽に見えても、PM の手が塞がればチーム全体が止まってしまう。一方で、現場のエンジニア一人ひとりがダンドリの視点を持ち、自ら動けるようになれば、チームのスピードと対応力は格段に高まる。

- 「なぜこれを作るのか」を理解し、的外れな実装による手戻りを防ぐ
- 判断に必要な事実・仮説・懸念を整理して、チームの意思決定を後押しする
- どこが詰まっているか（ボトルネック）に目を配り、PR の分割やレビューの手助けを進んで行う

これらは特別な役職についていなくても、現場でコードを書くエンジニア自身が日々の仕事の中で発揮できる立派な技術だ。みんなが少しずつダンドリを担うことで、誰か 1 人がボトルネックになるのを防ぎ、スムーズに前進し続けるチームが育っていく。

# 本書の要点整理

日々の開発で判断に迷ったときは、次の 4 つの原則に立ち返ってみてほしい。

1. **作業時間ではなくリードタイムを縮める**
   コードを書くスピードを上げること以上に、待ち時間や依存関係によるストップ、手元の抱え込み（WIP）を減らすことが、価値を早く届ける近道になる。
2. **不確実性を早く、小さく検証する**
   未知の要件や技術的な難所を後回しにせず、モックやスパイクを使って早めに白黒をつける。戻りにくい決定（One-way door）ほど、小さく試して裏を取る。
3. **ボトルネックを見極め、チーム全体で合わせる**
   個人の作業が終わったことだけに満足せず、チーム全体の流れを止めているボトルネックに手を貸し、滞りをなくす。
4. **提案は「相手の不安を減らす形」で届ける**
   改善提案を通すためには、相手の言葉（関心事）への翻訳、事実と仮説と懸念の切り分け、小さな検証（PoC）の提示、そして引き際（撤退基準）の約束が効果を発揮する。

# 明日からの実践ステップ

まずは、明日からできる小さな一歩から試してみよう。

| 現場の課題 | 最初のアクション |
| :--- | :--- |
| レビュー待ちが長い | PR を関心事ごとに細かく分け、動作確認のスクショや実行ログを添えてみる。 |
| 仕様や技術に不安がある | 数日かけていきなり作り始めず、「半日のスパイク（検証タスク）」を挟んで確かめてみる。 |
| 設計の経緯がわからなくなる | Issue やチケットに「決定事項」「試した代替案」「選んだ理由」を 3 行でメモ（ADR 化）しておく。 |

「読み・書き・プログラミング」に並ぶ、ソフトウェアエンジニアの基礎技術としての「ダンドリ」。日々の小さな詰まりを取り除く工夫の積み重ねが、自分自身の開発環境を心地よいものにし、チームの成果を底上げしていくはずだ。

# 参考書籍・知識体系

本書の論理構造は、以下の書籍および知識体系の知見に基づき、ソフトウェア開発の実務現場向けに再構成したものである。

- リチャード・P・ルメルト『良い戦略、悪い戦略』（日本経済新聞出版）
  - 診断、基本方針、首尾一貫した行動からなる「戦略のカーネル」の思考体系。
- 広木大地『エンジニアリング組織論への招待』（技術評論社）
  - 不確実性を「目的・方法・通信」に分解し、情報と意思決定を扱うアーキテクチャ。
- エリヤフ・ゴールドラット『ザ・ゴール』（ダイヤモンド社）
  - 全体最適を実現する制約理論（TOC）およびボトルネック管理の原則。
- ジョナサン・ラスマセン『アジャイルサムライ』（オーム社）
  - スコープ、時間、リソース、品質のトレードオフ管理とチーム運営。
- 木部智之『プロジェクトのトラブル解決大全』（クロスメディア・パブリッシング）
  - 現場の課題とリスクを構造的に可視化・分類する道具立て。
- PMI『PMBOK ガイド』／ PMAJ『P2M（プロジェクト＆プログラムマネジメント標準ガイドブック）』
  - プロジェクトマネジメントの国際的・標準的知識体系。
