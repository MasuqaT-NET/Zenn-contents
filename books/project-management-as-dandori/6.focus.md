# なぜ省力化・高速化が必要なのか

プロジェクトマネジメント（ダンドリ）を実践しようとするとき、多くの人が「管理のための管理（重厚なドキュメント作成、進捗確認のための長時間の会議、マイクロマネジメント）」に陥り、かえって現場のエンジニアリングを圧迫してしまうという罠に直面する。

本来のダンドリの目的は「もったいない（手戻りや待ち時間）を無くし、最短で価値を届けること」であるはずが、マネジメント自体が新たな「もったいない」を生み出してしまっては本末転倒である。

- **リソースの有限性と認知負荷の限界**:
  - エンジニアやチームにとって最も希少なリソースは「集中できる時間」と「認知的エネルギー」。
  - プロジェクトマネジメントの負荷が重すぎれば、本来注力すべき設計や実装のクオリティが犠牲になる。
- **ボトルネック（制約）に集中（フォーカス）するため**:
  - すべての課題やタスクに等しく全力を注ぐことは不可能であり、成果にも結びつかない。
  - プロジェクト全体の成果・スピードを決定づけている「ごく一部の急所（制約・ボトルネック・クリティカルパス）」を見極め、そこにリソースとエネルギーを集中投下するために、それ以外の工程や管理作業を徹底的に省力化する必要がある。
- **「専任の PjM がいない組織」において持続可能にするため**:
  - モダンなソフトウェア開発組織では、専任の PjM を置かず、エンジニアやテックリード、PdM がダンドリを分担することが多い。
  - 特定の専任者が一日中張り付かなければ回らない重厚な仕組みではなく、誰もが自然に回せる省力化されたダンドリでなければ継続しない。
- **手戻りと待ち時間という最大のムダを排除するため**:
  - 省力化とは「手抜き」ではなく、事前の「段取り八分」によって後工程の巨大なトラブルや待ち時間を未然に消し去ることである。

# 理論とアプローチ（フォーカスと高速化を支える 4 つの理論）

プロジェクトを無駄なく高速に進めるためには、直感や根性論ではなく、確立されたオペレーションズリサーチや生産管理・システム工学の理論をダンドリの道具として活用する。

## 1. クリティカルパス（Critical Path Method: CPM）

- **定義**:
  - プロジェクト全体のタスクの依存関係の中で、**「開始から完了まで最も時間がかかる一連のタスクの経路（最長経路）」**。
- **本質と特徴**:
  - **全体の最短納期を決定づける**: プロジェクト全体の最短所要期間は、クリティカルパスの長さと完全に一致する。
  - **スラック（余裕時間）の有無**:
    - クリティカルパス上のタスクはスラックが「ゼロ」。1 時間でも遅れれば、プロジェクト全体の納期がそのまま 1 時間遅延する。
    - 一方、クリティカルパスから外れた並行タスクにはスラック（余裕）が存在する。それらをいくら前倒しで高速化しても、プロジェクト全体の納期は 1 日も縮まらない。
- **ダンドリへの適用**:
  - 「今、何がクリティカルパス上にあるのか」をチーム全員が常に意識・把握する。
  - クリティカルパス上のタスクに最優先でリソースを投入し、仕様の不明点や外部依存などの障害を最優先で先回りして潰しておく（段取り八分）。

## 2. 制約理論（TOC: Theory of Constraints）

- **基本思想**:
  - エリヤフ・ゴールドラットが提唱したマネジメント理論（『ザ・ゴール』）。
  - **「システム全体のパフォーマンス（スループット）は、最も能力の低い工程（ボトルネック／制約）によってのみ決定される」**。
  - ボトルネック以外の工程をいくら個別最適化・高速化しても、全体の処理速度は上がらない。
- **局所最適の罠**:
  - ボトルネックの前工程が「空いているから」と大量に作業を進めると、ボトルネックの手前に未処理の仕掛品（WIP: レビュー待ち PR、確認待ち仕様など）が山積みになる。
  - これにより、コンテキストスイッチの増大、コンフリクトの多発、手戻り時の被害拡大が発生し、システム全体としてはかえって遅くなる。
- **TOC の 5 段階集中プロセス（ソフトウェア開発での実践）**:
  1. **制約を見つける（Identify）**:
     - 開発フローの中で、どこにタスクが最も滞留（山積み）しているかを特定する（例: テックリードの PR レビュー待ち、PdM の仕様決定待ち、QA 環境の空き待ち）。
  2. **制約を徹底活用する（Exploit）**:
     - 制約となっている人や工程に、無駄な時間を使わせない。
     - 例: レビューが制約なら、テックリードから雑務や定例会議を免除する。前工程のエンジニアはレビューしやすいように PR を小さく分割し、コンテキストを丁寧に書く。
  3. **他のすべてを制約に従属させる（Subordinate）**:
     - 制約の処理ペースに合わせて前工程のペースを調整する（WIP 制限）。
     - 前工程のメンバーは、必要であれば手を止めて制約の支援（ペアプロ、テスト自動化、下準備など）に回る。
  4. **制約の能力を高める（Elevate）**:
     - 制約自体のキャパシティを構造的に引き上げる。
     - 例: CI/CD でのテスト自動化によるレビュー負荷軽減、モブプロ導入による知見の共有とレビュアーの多能工化、権限移譲。
  5. **惰性を防ぎ、次の制約へ戻る（Repeat / Avoid Inertia）**:
     - 1 つのボトルネックが解消されると、必ず別の工程が新たな制約になる（例: レビューが早くなると、今度はリリースや QA が詰まる）。改善を止めず、常に次の急所へフォーカスし続ける。

## 3. CCPM（クリティカルチェーン・プロジェクトマネジメント）

- **定義**:
  - TOC の考え方をプロジェクトマネジメントに応用した手法。
  - タスクの論理的な依存関係だけでなく、**「作業を行う人員（リソース）の競合」**も考慮した最長経路（クリティカルチェーン）をマネジメントの核とする。
- **従来の個別見積もりが破綻する人間の行動心理**:
  - **パーキンソンの法則**: 「仕事の量は、与えられた時間をすべて使い切るまで膨張する」。余裕を持たせたスケジュールを与えると、その期間いっぱいまで作業を延ばしてしまう。
  - **学生症候群**: 「締め切り直前まで本気で着手しない」。どれほどバッファを持たせても直前まで手を付けず、想定外のトラブルで結局納期に遅れる。
  - **安全余裕の浪費と遅れの伝播**:
    - 個々のタスクに安全バッファを潜り込ませても、「早く終わった」ことは報告されず隠される（次回から見積もりを削られるのを恐れるため）。
    - したがって「早く終わった時間の余裕」は後工程に伝播せず、「遅れた影響」だけがドミノ倒しのように後工程に波及する。
- **CCPM による解決策**:
  - **個別タスクからバッファを剥ぎ取る**:
    - 各タスクの見積もりは「50%の確率で完了する野心的な見積もり（無駄な安全余裕を入れない）」とする。
  - **プロジェクトバッファの集約**:
    - 剥ぎ取ったバッファを各タスクに分散させず、プロジェクト全体の末尾に**「プロジェクトバッファ」**として一括配置する（クリティカルチェーンに合流する枝タスクには「合流バッファ」を置く）。
  - **バッファマネジメントによる可視化**:
    - 個々のタスクが予定通り終わっているかどうか（進捗率）で人を管理しない。
    - **「プロジェクトの進捗率」に対して「プロジェクトバッファが何％消費されたか」**をグラフ（緑・黄・赤のシグナルゾーン）で監視する。
    - 個人の遅れを責めるのではなく、「プロジェクトバッファが健全かどうか」を全員で注視し、黄色や赤色に入ったら全員でボトルネックの火消しに走る。

## 4. システム思考（Systems Thinking）

- **定義**:
  - 物事を要素単体ではなく、要素間の「相互関係」「因果ループ」「時間的遅れ（ディレイ）」を含んだ全体システムとして捉える思考法。
- **局所最適と全体最適**:
  - 個々のエンジニアが目の前のチケットを素早く終わらせても、チーム全体としてプロダクトの価値提供スピードが上がっていなければ意味がない。
  - 「開発者がコードを書くスピード」よりも「価値がエンドユーザーに届くパイプライン全体の流量」を重視する。
- **因果ループと「遅れ（ディレイ）」**:
  - 例（忙しさの悪循環）:
    - 開発者が忙しい → テストやドキュメントを省いて雑にリリースする → 後でバグや問い合わせが急増する → 調査と修正に追われてさらに忙しくなる。
  - システム思考では、このような自己強化ループの存在を見抜き、対症療法（人手を増やす、残業する）ではなく、根本的なループを断ち切る**「レバレッジ・ポイント（急所）」**に手を入れる（例: 自動テストの導入、レビュー基準の明確化）。

# プロセス・儀式：敏感な人だけに負担が行かない仕組み

リスクやボトルネックの発生に最も早く気づくのは、往々にして「周囲への気配りができる人」「経験豊富なシニア」「危機管理意識が高い敏感な人」である。
しかし、彼らの属人的な気づきや善意に依存していると、次のような組織的破綻を招く。

- **属人性の罠**:
  - 敏感な人だけに問題対応や調整の負荷が集中し、その人がバーンアウト（燃え尽き）する。
  - その人が不在になった途端にプロジェクトが立ち往生する。
  - 周囲のメンバーが「あの人が気づいて何とかしてくれるだろう」と受け身になり、当事者意識が育たない。

したがって、**「誰が見ても客観的に異変や詰まりに気づける仕組み」**をプロセスと儀式の中に埋め込む必要がある。

## 1. カンバンボードと WIP（仕掛品）制限による「違和感の可視化」

- **可視化**:
  - 「誰が今何をやっているか」だけでなく、「どこにタスクが滞留しているか」を一目でわかるようにする。
  - 「レビュー待ち」「QA 待ち」「仕様確認中」のカラムにカードが積み上がっている状態は、システムが目詰まりを起こしている明白なシグナルである。
- **WIP（Work In Progress）制限**:
  - 同時に着手できるタスクの上限数を設定する（例: レビュー待ちは最大 3 件まで）。
  - 上限に達したら、前工程の新しいタスクには絶対に着手してはならない。
  - 全員でレビューを消化するか、詰まりの原因を解消することを最優先にする。これにより、敏感な人が声を上げなくても、システム的に作業の偏りが是正される。

## 2. デイリースタンドアップの変革（タスク主導の朝会）

- **個人報告会からの脱却**:
  - 「昨日やったこと」「今日やること」を順番に読み上げるだけの報告会は形骸化しやすく、問題を発見できない。
- **ボードの右側（完了に近い側）から見る**:
  - カンバンボードの右側（リリース直前・レビュー中・QA 中）から順に確認していく。
  - 「完了に一番近いこのタスクは、なぜ昨日完了しなかったのか？」「何が邪魔（ブロッカー）しているのか？」「どうすれば今日中に完了（Done）に持っていけるか？」を議論する。
  - 個人を問いただすのではなく、「タスクの流れを止めている障害をチーム全員でどう取り除くか」にフォーカスする。

## 3. アンドン（行灯）文化とヘルプシーキングの低コスト化

- **異常停止の仕組み（アンドン）**:
  - トヨタ生産方式の「アンドン」のように、作業者が問題を発見した際、即座にラインを止めて周囲にアラートを出せる仕組み・文化を整える。
- **ヘルプシーキング（助けを求めること）のルール化**:
  - 「30 分悩んで自力で解決できなければ、必ず誰かに相談するかハドルミーティングを開く」といった客観的なルール（タイムボックス）を設ける。
  - 「助けを求めること」は個人の恥や能力不足ではなく、「チームの時間を浪費させないための優れたダンドリ」として称賛する文化を醸成する。

## 4. 定期的なふりかえり（レトロスペクティブ）によるプロセスの自己修復

- **待ち時間・手戻りの点検**:
  - スプリントやマイルストーンの終わりに、「今期、最も長かった待ち時間はどこか？」「最も大きな手戻りは何だったか？」を振り返る。
- **ダンドリの改善アクション**:
  - 「気合で頑張る」ではなく、「次回からこのチェックリストを使う」「この段階で事前レビューを挟む」といった、プロセス自体の修正（再ダンドリ）に落とし込む。

# 仕組み化・自動化・セルフマネジメント

プロジェクトマネジメントを真に省力化・高速化する最終的な手段は、ツールの力を使った**「自動化」**と、メンバー一人ひとりが自ら段取りを組む**「セルフマネジメント」**である。

## 1. 数値化の魔力（メトリクスによる事実ベースの把握）

- **客観的なデータによる会話**:
  - 「なんとなく遅れている」「みんな忙しそう」といった主観ではなく、数値データを用いて現状を把握する。
- **Four Keys（DORA メトリクス）の活用**:
  - デプロイ頻度（Deployment Frequency）
  - 変更リードタイム（Lead Time for Changes: コミットから本番稼働までの時間）
  - 変更障害率（Change Failure Rate）
  - 障害復旧時間（Time to Restore Service / MTTR）
  - これらを計測することで、パイプラインのどこに遅れや手戻りの原因があるかが客観的に特定できる。
- **フロー効率（Flow Efficiency）とリードタイム分析**:
  - **フロー効率 =「実際に手が動いていた作業時間」÷「着手から完了までの総経過時間（リードタイム）」**。
  - 多くの開発現場では、フロー効率は 10〜15% 程度にとどまる。つまり、作業時間の 85% 以上は「誰かの確認待ち」「環境待ち」「放置」などの待ち時間である。
  - この数値を可視化することで、「開発者のキーボードを叩くスピードを上げさせる」のではなく、「待ち時間（もったいない）を削るダンドリ」がいかに効果的であるかをチーム全体で共有できる。

## 2. 自動化によるマネジメント負荷の徹底削減

- **CI/CD パイプラインによる手作業と待ち時間の排除**:
  - 静的コード解析、単体テスト、統合テスト、ビルド、デプロイ、プレビュー環境の払い出しを完全自動化する。
  - 「テストが通っているか」「動作確認環境が準備できたか」を手動で確認・調整するコミュニケーションコストをゼロにする。
- **Bot と通知の活用によるリマインドの自動化**:
  - レビュー依頼の放置、未アサインの課題、期限が迫ったタスクなどを Bot が自動検知して Slack 等に通知する。
  - 人間が気まずい思いをしながら「あの件どうなりましたか？」と催促する精神的コストと手間を省く。
- **コミュニケーションとドキュメントのテンプレート化**:
  - PR テンプレート（背景、変更点、テスト手順、レビュー観点）。
  - Issue / バグ報告テンプレート。
  - ADR（Architecture Decision Record / 設計決定の記録）。
  - 必要な情報があらかじめ網羅されることで、「前提の聞き返し」「仕様の確認待ち」といった手戻りを最小化する。

## 3. 自律的チームへの進化とセルフマネジメント

- **情報と判断基準の透明化**:
  - プロジェクトの目的（Why/What）、クリティカルパス、優先順位の基準（荒ぶる四天王のトレードオフ）、制約が全員に共有されていれば、個々のエンジニアが現場で自律的に正しい判断を下せる。
  - マネージャーにいちいち伺いを立てる「判断待ちの遅延」が消滅する。
- **専任 PjM の役割の移行（管理者から環境設計者へ）**:
  - マネージャーの仕事は、個別のタスクを割り振って監視すること（マイクロマネジメント）ではない。
  - **「チームが目詰まりを起こさずに滑らかに価値を流し続けられる仕組み（パイプライン）を設計し、障害を取り除くこと」**へと進化する。
- **全員がダンドリの技術を持つ（セルフマネジメント）**:
  - チーム全員が「ボトルネック」「クリティカルパス」「もったいないの排除」を共通言語として持ち、各自が自身のタスクの段取りを自律的に整える。
  - これにより、特定個人への依存（属人化）が解消され、PjM 専任者がいなくても自走する強靭な開発チームが実現する。

# まとめ：フォーカスと省力化がもたらす本質

- **省力化とは手抜きではない**:
  - 「もったいない（手戻り・待ち時間・不要な管理工数）」を極限まで削ぎ落とし、全体のアウトカムを決定づける最重要の急所（ボトルネック・クリティカルパス）に全エネルギーを注ぎ込むための高度なダンドリである。
- **理論 × プロセス × 自動化の三位一体**:
  - 理論（CPM、TOC、CCPM、システム思考）によって「どこにフォーカスすべきか」を見定め、
  - プロセスと儀式（カンバン、WIP 制限、スタンドアップ、アンドン）によって「属人化を防ぎ組織的に気づき」、
  - 仕組み化と自動化（メトリクス、CI/CD、テンプレート、自律性）によって「マネジメントコストそのものを消去」する。
- これらを通じて、最小の労力で、予測可能性高く、最短・最速で継続的な価値を届けられる状態をつくり出す。
