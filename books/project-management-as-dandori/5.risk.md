---
title: "不確実性・リスク・問題"
---

現場では「リスク」と「課題・問題」が曖昧に使われがちだが、これらを混同すると、問題が起きてからの場当たり的な「火消し」に終始することになり、手戻りや待ち時間という莫大な「もったいない」を垂れ流すことになる。
本章では、不確実性・リスク・問題の連鎖構造を解き明かし、タスク起点ではなく「リスク起点」でプロジェクトを捉える段取りの技術を体系化する。

# 1. 連鎖の捉え方

プロジェクトにおいて、トラブルが唐突に降って湧くことはほとんどない。あらゆる問題には「発端」と「プロセス」が存在する。

- **因果の連鎖ループ**:
  $$\text{不確実性（土壌）} \longrightarrow \text{リスク（可能性）} \longrightarrow \text{事象（トリガー）} \longrightarrow \text{問題・課題（現実）}$$

  1. **不確実性（Uncertainty）**:
     - **状態**: 情報の不足や状況の曖昧さによって、未来の予測が定まらない「土壌・環境」。
     - **具体例**: 「新しく採用するクラウドサービスの挙動がまだよく分かっていない」「顧客の業務要件に曖昧な部分が残っている」。
  2. **リスク（Risk）**:
     - **状態**: 不確実性の土壌から生じる、プロジェクトの目標達成にプラスまたはマイナスの影響を与え得る「未来の不確かな事象・揺らぎ」。まだ起きていない。
     - **具体例**: 「新サービスの API レート制限に引っかかり、想定のパフォーマンスが出ないかもしれない（脅威）」「他社ツールの導入で工数を 30% 削減できるかもしれない（好機）」。
  3. **事象（Event / Trigger）**:
     - **状態**: リスクが確率の壁を越えて現実化する瞬間。トリガーが引かれること。
     - **具体例**: 「負荷テストで実際にレート制限エラー（429 Too Many Requests）が多発した」。
  4. **問題・課題（Issue / Problem）**:
     - **状態**: 事象が発生した結果、プロジェクト目標に実害が生じており、今すぐ是正・修復のための対処（ワークアラウンドや仕様変更）が必要な「現在の状態」。
     - **具体例**: 「システムが要件のレスポンスタイムを満たせず、リリース判定をパスできない。至急、キャッシュ層の設計と実装が必要である」。

- **決定的な違いは「時間軸」と「確定性」**:
  - **リスク ＝ 未来の概念（不確定・確率の領域）**: まだ起きていないため、知恵と段取りによって「回避」や「軽減」ができる。予防コストは一般に小さい。
  - **問題・課題 ＝ 現在・過去の概念（確定・現実の領域）**: すでに起きてしまっているため、もはや「防ぐ」ことはできず、「対処・火消し・復旧」するしかない。対処コストは極めて大きい。
  - **「火消し」から「段取り」へのパラダイムシフト**:
    - 問題が発生してから慌てて動くのは「対症療法（火消し）」に過ぎない。
    - 段取りの本質は、問題化する前の「リスク」の段階、さらにはその源泉である「不確実性」の段階で手を打ち、問題そのものを未然に蒸発させることにある。

# 2. 全体としての捉え方

- **未知領域: 氷山の一角**:
  - プロジェクトの初期段階や要件定義フェーズで見えているタスクや仕様は、全体から見れば「氷山の一角（水面上）」に過ぎない。
  - 水面下には、まだ言語化されていないステークホルダーの期待、見落とされたシステム間の依存関係、技術的な落とし穴といった巨大な「未知領域（アンノウン・アンノウンズ）」が潜んでいる。
  - タスクリスト（見えている氷山）の進捗だけを管理して安心していると、水面下の未知領域に激突してプロジェクトは沈没する。

- **受け取り方・管理**:
  - リスクを「あってはならない悪」と捉えて隠蔽する文化はプロジェクトを破滅させる（PMBOK でもリスクには好機も含まれるとされる）。
  - すべてのリスクをゼロにすることは不可能であり、リスクをゼロにしようとすればプロジェクトのスピードと挑戦意欲が失われる。
  - 重要なのは、有限のリソース（時間・予算・人員）の中で、**「どのリスクに向き合って低減し、どのリスクを敢えて受け入れる（受容する）か」** というトレードオフの意思決定（リスクテイキングの設計）を行うことである。

- **検知の技術: 個人では検知しきれない**:
  - 不確実性や潜在リスクを、プロジェクトマネージャーやテックリードが単独で洗い出すことには認知的限界がある。
  - **集合知の活用**: 開発者、QA、インフラ、デザイナー、ビジネス担当者など、異なるコンテキストと専門性を持つ多様な視点を持ち寄ることで初めて死角が消える。
  - **勘と経験・敏感な人（炭鉱のカナリア）**:
    - 「ドキュメント上は問題なさそうに見えるが、なんとなく嫌な予感がする」「過去の似た案件でここでハマった」という現場の直感や違和感は、極めて高精度なリスクシグナルである。
    - チーム内の「違和感に敏感な人」の声を決して「エビデンスがない」と一蹴せず、真剣に耳を傾ける。
  - **雑談と心理的安全性の重要性**:
    - 公式な進捗会議（定例 MTG）では、確定した情報しか報告されにくい（「問題ありません」と言いがち）。
    - 「実はここ、ちょっと自信がなくて…」「この仕様、後で揉めそうな気がするんですよね」といった不穏な匂い（リスクの種）は、日々の雑談、ペアプロ・モブプロの合間、立ち話、分報（Slack の times チャンネル）などのインフォーマルなコミュニケーションからこそ立ち上る。

- **確率の霧と「掛け算」の性質**:
  - プロジェクトの未来は「確率の霧」に覆われている。
  - [EM.FM Re.44](https://www.youtube.com/watch?v=o8Mfd2ougS4) にて広木大地氏が指摘するように、**タスクとリスクには数学的な振る舞いの決定的違い**がある。
    - **タスクは「足し算（加算）」**:
      - タスクをこなす作業時間は足し算で積み上がる。
      - 個々のタスクの完了時間に多少のバラつきがあっても、タスク数が多くなれば中心極限定理によって全体の工数は「正規分布」に収束する（平均値付近に落ち着きやすい）。
    - **リスクは「掛け算（乗算・スパイス）」**:
      - リスクは「ある工程が 1.2 倍に膨らむ」「依存関係の遅延で全体が 1.5 倍になる」というように、プロジェクト全体に対して**掛け算（比率）**で作用する。
      - 掛け算の揺らぎが複数重なり合うと、全体の工数分布は正規分布ではなく**「対数正規分布（ロングテール）」**を描く。
      - これにより、平均値から何倍も乖離した破滅的な遅延（外れ値）が発生する。
  - 「タスクの積み上げ（足し算）見積もり」だけではプロジェクトの遅延を防げないのは、この「掛け算のリスク」を勘案していないからである。外れ値による破綻を防ぐには、掛け算の連鎖を断ち切る段取りが必要になる。

- **リスクベースのマネジメント（Risk Based Management）**:
  - タスク消化の進捗率（バーンダウンチャート）だけを追うマネジメントから、**「プロジェクトの残存リスクをどれだけ減らせたか」を測るマネジメント**への転換。
  - **リスクベーステスト（Risk Based Test: RBT）の思想をプロジェクト全体へ適用**:
    - テストの世界では、限られたテスト期間ですべてを網羅できないため、「障害発生確率 × 障害時の影響度」が高いリスク領域にテストリソースを集中的に配分する（リスクベーステスト）。
    - 同様にプロジェクトマネジメント全体においても、不安要素や影響度の大きい「クリティカルな不確実性」から優先的に着手し、早い段階で検証・解消する（リスクドリブンなタスク順序の設計）。

# 3. 不確実性

プロジェクトを覆う霧の正体である「不確実性」を解剖し、どこから手をつけるべきかを明らかにする。

- **いろいろな不確実性の種類（第 3 章の知見との接続）**:
  - **1. 目的不確実性（Why / What）**:
    - 「何を作るべきか」「誰のどんな課題を解決するのか」の不確実性。
    - 顧客や市場のニーズの揺らぎ、受け入れ基準の曖昧さ。
  - **2. 手段不確実性（How）**:
    - 「どう実現するか」「技術的に実現可能か」の不確実性。
    - 新しいアーキテクチャ、未知のライブラリ、外部 API の信頼性、非機能要件（性能・スケーラビリティ）。
  - **3. 通信不確実性（Who / Communication）**:
    - 「ステークホルダー間で正しく情報が伝わっているか」の不確実性。
    - 暗黙の前提の食い違い、専門用語の認識ズレ、心理的障壁による情報遮断。

- **コラム: 「上流」は不確実性の塊**:
  - なぜウォーターフォール開発や大規模プロジェクトにおいて、「上流工程（要件定義・基本設計）」の不備が致命傷になるのか。
  - 上流工程とは、最も情報が少なく、目的不確実性と通信不確実性が最も高濃度に凝縮された「不確実性の塊」だからである。
  - 上流でのわずかな仕様のブレ（1 のズレ）は、下流（詳細設計 → 実装 → テスト）へと進むにつれて掛け算で増幅され、リリース直前には「100 の手戻り」となって爆発する（手戻りコストの指数関数的増大）。
  - したがって、上流工程を「机上のドキュメント作成」だけで終わらせてはならない。プロトタイプや PoC、モックアップを用いた早期のフィードバックループを回し、上流の不確実性を手戻りの安いうちに強制的に引き下げることが最強の段取りとなる。

# 4. リスク

- **そもそもリスクとは何か（PMBOK 第 7 版の定義）**:
  - 「発生が不確か（確率的）なイベントまたは状態であり、もし発生したら、プロジェクト目標にプラス（好機：Opportunity）あるいはマイナス（脅威：Threat）の影響を及ぼすもの」。
  - リスクとは「悪いこと（脅威）」だけでなく、「予期せぬチャンス（好機）」も内包する未来の揺らぎ全般を指す。

- **リスクが持つ多面的な性質**:
  1. **連鎖する（ドミノ倒し）**:
     - リスクは単体で完結せず、あるリスクの顕在化が引き金となって次々と別のリスクを誘発する（例: 設計不備 → 仕様齟齬 → 手戻り発生 → テスト期間圧迫 → 品質低下 → スケジュール遅延）。
     - IPA『ITプロジェクトのリスク予防への実践的アプローチ』でも強調される通り、リスクを「点」ではなく「因果のつながり（チェーン）」として捉えることが重要。上流の根本原因（起点のドミノ）を倒さないように手を打てば、後続の連鎖リスクを一挙に予防できる。
  2. **階層性がある（マトリョーシカ）**:
     - リスクは多層的な入れ子構造を持つ。
     - 最上位の「プロジェクト失敗・納期遅延」の下に中位の「特定機能の実装遅延」があり、その下に下位の「外部 API の仕様未確定」「担当エンジニアのスキル不足」などがぶら下がっている。
     - 上位レベルの抽象的なリスクだけを見ていても具体策が打てず、下位の細かなリスクばかり見ていても全体像を見失う。両者を往復する視座が必要。
  3. **分類可能である**:
     - リスクに名前を与え、カテゴリ（人的・技術的・外的・管理的など）に分類した瞬間に、人間はそれを構造的に管理できるようになる。
     - 分類によって抜け漏れを防ぎ、弱点の偏りを発見し、チーム内の共通言語化が進む。
  4. **乗算的に作用する（前述）**:
     - リスクは足し算ではなく掛け算で作用し、対数正規分布（ロングテール）を形成して想定外の壊滅的遅延を引き起こす。
  5. **見えづらい（地雷）**:
     - 順調に見えるプロジェクトほど、水面下でリスクが静かに進行している（「今は問題なさそう」というバイアス）。
     - 兆候（シグナル）を拾う感度を高め、見えづらいリスクを意識的に言語化・可視化する必要がある。
  6. **評価にばらつきが出やすい（万華鏡）**:
     - 開発者は「技術的難易度」を恐れ、PM は「納期・工数」を恐れ、ビジネス側は「要件不足」を恐れるように、立場によってリスクの評価（確率・影響度）は大きく異なる。
     - 個人の主観に依存させず、共通の評価軸を設け、複数人の視点を統合して合意形成を図る必要がある。
  7. **対応可能性によって整理できる**:
     - 「コントロールできるリスク（社内の技術選定、リソース配分など）」と「コントロールできないリスク（取引先の倒産、法改正、自然災害など）」がある。
     - コントロール不能なリスクに対して無理に予防策を講じるのはリソースの無駄であり、それらは「受容」した上で BCP（事業継続計画）やコンティンジェンシー予備（バッファ）で備える。
  8. **時間とともに収束する（霧の晴れ間）**:
     - プロジェクトが進むにつれて情報が増加し、不確実性は減少し、リスクの幅は狭まっていく（不確実性コーン: Cone of Uncertainty）。
     - PMBOK でいう「段階的詳細化（Progressive Elaboration）」を前提に、定期的にリスクを見直し続ける。

- **標準リスクモデル（スミス＆メリット）が示す「構造としてのリスク」**:
  - プレストン・G・スミスとガイ・M・メリットが『実践・リスクマネジメント』で提唱したモデル。
  - リスクを単なる箇条書きではなく、以下の**因果関係のネットワーク**として捉える。
    $$\text{事実（既知の前提）} \longrightarrow \text{リスク事象ドライバー} \longrightarrow \text{リスク事象} \longrightarrow \text{影響ドライバー} \longrightarrow \text{影響（損失量）}$$
  - **構造で捉える最大のメリット**: 「どこに手を打てばリスクを無力化できるか（変えられるリスクの急所）」が一目瞭然になる。
    - 事象の発生確率を下げる介入点（リスク事象ドライバーへの対策）
    - 起きてしまった場合の影響を食い止める介入点（影響ドライバーへの対策）

- **チームで実践するリスク洗い出し手法**:
  - 感覚的・ボトムアップな手法と、構造的・トップダウンな手法を組み合わせる。
  1. **プレモーテム（事前分析 / Pre-Mortem）**:
     - 「プロジェクトが 1 年後に大失敗し、大炎上した」と仮定し、その原因をチーム全員で過去形で逆算して洗い出す（タイムマシン手法）。
     - 失敗を前提とすることで、普段は言いにくい懸念や本音を心理的安全に吐き出せる。
  2. **象・死んだ魚・嘔吐（Elephant, Dead Fish, Vomit）**:
     - チームの感情や暗黙知を掘り起こす対話型アプローチ。
     - **象（Elephant in the room）**: 誰もが気づいているのに、空気を読んで口に出せない巨大な問題。
     - **死んだ魚（Dead Fish）**: 時間が経つにつれて悪臭を放ち、放置すると取り返しのつかない事態になる問題。
     - **嘔吐（Vomit）**: とにかく胸の中にある不安や愚痴を全部吐き出してみる。
  3. **RBS（Risk Breakdown Structure / リスクブレークダウンストラクチャ）**:
     - WBS のように、リスク源を「技術」「外部」「組織」「プロジェクト管理」といった階層構造で体系的にブレークダウンして網羅する。
  4. **FTA（Fault Tree Analysis / フォールトツリー解析）**:
     - 頂上事象（例: 「システムダウン」）から「なぜ？」を繰り返してツリー状に因果関係を掘り下げる論理的手法。
  5. **IPA リスク事象ドライバー一覧**:
     - 過去の大規模 IT プロジェクトの失敗事例から抽出されたチェックリストを活用し、発想の盲点を補う。

- **リスクの分析・評価・可視化**:
  - **リスクスコアの算出**: $\text{リスクスコア} = \text{発生確率} \times \text{影響度}$
  - **4 象限マトリクス & ヒートマップ**:
    - 横軸に発生確率、縦軸に影響度を取り、マッピングする。
    - **赤領域（右上: 確率高×影響大）**: 最優先で予防・回避策を講じるべき領域。
    - **黄領域（確率高×影響小、または確率低×影響大）**: 軽減策を打つか、発生時のコンティンジェンシープランを用意する領域。
    - **白/緑領域（左下: 確率低×影響小）**: 受容し、定期モニタリングに留める領域。
  - **定性分析から定量分析へ**:
    - まず定性分析（大・中・小などのランク付け）で全体を俯瞰し、重要なリスクのみ「期待損失額（発生確率 × 損失金額）」を算出して定量評価する。
    - 「対策コスト < 期待損失額」であれば、その対策は投資対効果が高いと合理的に判断できる。

- **リスク対応戦略（PMBOK 第 7 版）**:
  - **脅威（マイナスリスク）への 5 大戦略**:
    1. **回避（Avoid）**: リスクの原因そのものを排除する（例: 危険な技術の採用を取りやめ、枯れた実績のある技術に変更する、スコープから外す）。
    2. **軽減（Mitigate）**: 発生確率や影響度を下げる（例: 早期に PoC を実施する、自動テストを導入する、コードレビューを二重化する）。
    3. **転嫁（Transfer）**: リスクの影響を第三者に移転する（例: 保険への加入、SLA 付きのマネージドサービス利用、外部委託契約）。
    4. **受容（Accept）**:
       - **能動的受容**: 起きることを前提として予備バッファ（時間・予算）を確保し、コンティンジェンシープランを策定しておく。
       - **受動的受容**: 影響が軽微なため、起きたらその場で対応する。
    5. **エスカレーション（Escalate）**: プロジェクトチームの権限を超えるリスク（経営判断や全社方針に関わるもの）を上位層やステークホルダーに移管する。
  - **好機（プラスリスク）への戦略**:
    - **活用（Exploit）**（確実に発生させる）、**共有（Share）**（パートナーと連携して利益を最大化）、**強化（Enhance）**（確率や影響を底上げ）、**受容（Accept）**（来たら乗る）。

- **リスク登録簿（Risk Register）の生きた運用**:
  - 作って満足する静的なエクセルではなく、週次定例やスプリント計画で見直される動的なダッシュボード。
  - リスク管理の 5 ステップ（計画 → 特定 → 分析 → 対応策の実行 → モニタリング・改善）を継続的に回す。
  - **鉄則**: **「リスクが顕在化したら、即座に『課題（Issue）』へステータスを昇格させ、別の管理フロー（課題管理）に切り替える」**。

# 5. 問題

- **実際起きて対処が必要なもの（課題・障害・インシデント）**:
  - リスクの顕在化、あるいは予期せぬ未知の事象によって、プロジェクトに現実の障害が生じている状態。
- **問題発生時の段取りの鉄則**:
  1. **コンテインメント（影響の局所化・封じ込め）**: 被害の拡大を防ぐ（例: 障害箇所の切り離し、ロールバック、機能の一時停止）。
  2. **透明なエスカレーション**: 第 3 章で整理した「通信路」を使い、事実（Fact）を隠さず関係者へ迅速に共有する。
  3. **復旧と是正（ワークアラウンド）**: 暫定対応でサービスや開発を動かし、その後に恒久対応を行う。
- **再発防止と学習ループ（未知を既知へ）**:
  - なぜその問題が起きたのか、根本原因分析（ポストモーテム / なぜなぜ分析）を実施する。
  - 得られた教訓（Lessons Learned）を、組織の「リスク事象ドライバー一覧」やチェックリストに還元し、次のプロジェクトでは「事前に検知可能なリスク」へと昇華させる。

# 6. これらへのアクション

不確実性、リスク、問題をコントロールし、プロジェクトの手戻りと待ち時間を削るための具体的プラクティス。

- **各種の不確実性の排除プラクティス**:
  - **目的不確実性の排除**:
    - プロトタイプや Figma モックを用いた早期のユーザー検証・関係者レビュー。
    - 「完了の定義（Definition of Done）」や受け入れ基準（Given-When-Then）を開発着手前に握り合う。
  - **手段不確実性の排除**:
    - **スパイク（Spike）ソリューション**: 本実装に入る前に、技術的な実現可能性だけを検証する数時間〜数日のタイムボックス付きの使い捨てコードを書く。
    - アーキテクチャの早期検証（トレーサー・バレット: 細い一本の糸を E2E で通してみる）。
  - **通信不確実性の排除**:
    - ドメイン用語のユビキタス言語化、ADR（Architecture Decision Records）による意思決定理由の記録。
    - 定例会議に頼らず、非同期かつオープンなチャンネルでの情報流通を徹底する。

- **段階的詳細化（Progressive Elaboration）**:
  - 「最初からすべてを決めることはできない」という現実を受け入れる。
  - **ローリングウェーブ計画法（Rolling Wave Planning）**:
    - 直近のスプリントやマイルストーン（手の届く範囲）は細部まで高解像度にタスク化する。
    - 2〜3 ヶ月先の未来は粗い粒度（エピックやマイルストーンレベル）に留めておき、霧が晴れて情報が集まるにつれて順次詳細化していく。
  - これにより、「精緻に作った計画が初期の前提崩れで全面やり直しになる」という最大の手戻り（もったいない）を防ぐ。

- **まとめ: タスクではなくリスクを見ることで「もったいない」を削る**:
  - タスクの進捗を管理するだけでは、プロジェクトは守れない。タスクはあくまで「現在見えている作業」に過ぎないからである。
  - プロジェクトマネジメントの本質は、**水面下に潜む不確実性を凝視し、リスクの掛け算によるロングテールの爆発を予見し、問題化する前に先回りして芽を摘み取ること**にある。
  - リスク起点でプロジェクトを捉え、不確実性を小さなステップで段階的に手なずけていくことこそが、エンジニアリングにおける最高の「段取り」である。
