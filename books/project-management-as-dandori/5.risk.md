---
title: "不確実性・リスク・問題"
---

ソフトウェア開発において、未知の要素や障害の発生を完全に予見・排除することは不可能である。プロジェクトマネジメントにおけるリスク管理の目的は、未来の完全予測ではなく、**「致命傷となる障害を回避し、障害発生時にも迅速に復旧・適応できる余白を確保すること」** である。

本章では、混同されやすい概念を整理し、手戻りや障害の被害を最小限に抑えるためのリスク管理手法を解説する。

# 概念の定義：不確実性・リスク・事象・問題

開発プロセスの時間軸に沿って、以下の 4 つの概念を明確に区別する。

```mermaid
flowchart LR
    uncertainty["不確実性<br>（情報不足・未知の状態）"] -->|具体化| risk["リスク<br>（発生しうる不確実な事象）"]
    risk -->|発生| event["事象<br>（実際に起きた出来事）"]
    event -->|損失発生| problem["問題<br>（現在対処すべき障害）"]
```

1. **不確実性（Uncertainty）**：情報や知見が不足しており、将来の結果を確定的に予測できない状態。「外部 API の詳細なレート制限仕様が未確認である」など。
2. **リスク（Risk）**：発生するかどうかは不確実だが、もし発生した場合にプロジェクトの目的達成に悪影響を及ぼす具体的なシナリオ。「外部 API のレート制限により、夜間バッチが翌朝までに完了しない可能性がある」など。
3. **事象（Event）**：実際に発生した客観的な出来事。「深夜バッチ実行中に外部 API から HTTP 429 Too Many Requests が返却された」など。
4. **問題（Problem / Issue）**：すでに発生し、目的達成を阻害しているため、即座に対処が必要な損失状態。「夜間バッチの停止により、当日朝の顧客データが反映されていない」など。

「問題」に発展してから対応する場合のコストは、手前の「不確実性」や「リスク」の段階で対策を講じるコストに比べて大幅に増大する。

# タスク管理だけではプロジェクトが破綻する要因

チケット管理ツール（Jira, GitHub Issues 等）で管理されるタスク一覧は、「すでに既知となっている作業」を追跡するための道具にすぎない。水面下に存在する不確実性を管理しないままタスクだけを消化しても、プロジェクトの破綻は防げない。

## 1. 依存関係による遅延の非線形性

タスクの遅延は線形（足し算）ではなく、非線形（掛け算）で全体へ波及する。仕様確定が 0.5 日遅延した結果、API 実装の着手がずれ込み、レビュワーの空き時間を逃して 2 日間滞留し、QA の検証スロットを逃してテストが翌週に延期されるといったように、依存関係の連鎖によって遅延は指数関数的に拡大する。

## 2. 戻しにくい決定（One-way door）の先送り

意思決定は、その可逆性に応じて以下の 2 種類に分類できる。

- **可逆な決定（Two-way door）**：誤った判断であっても、低コストですぐにロールバック可能な決定。UI の文言、内部関数の命名、ログフォーマットなど。現場の裁量で迅速に判断し、検証を優先すべき対象である。
- **不可逆な決定（One-way door）**：一度決定して進めると、後戻りや変更に多大な工数とリスクを伴う決定。DB スキーマ設計、外部決済基盤の選定、マルチテナント分離方式など。

プロジェクト終盤で One-way door の誤りが発覚した場合、それまでに記述したコードの大部分が破棄される手戻りが発生する。したがって、**「不可逆な決定ほど、初期段階で小さな検証を行い、早期に妥当性を確認する」** ことが鉄則となる。

## 3. 開発中の違和感の早期言語化

「このデータ構造では将来のスケーラビリティに無理が生じるのではないか」「このバリデーション仕様では境界値で不整合が起きないか」といった、開発中にエンジニアが覚える技術的懸念は、潜在的リスクのもっとも早期の兆候である。これらを属人的な勘にとどめず、事実と仮説を分けて早期にチームへ共有する運用が求められる。

# リスクの構造化記述

リスクを検討する際は、以下の 3 要素で記述することで、講ずべき具体的な対策を明確化できる。

> **「【原因・条件】により、【事象】が発生した場合、【目的への影響】が生じる可能性がある」**

- **不十分な記述例**：「大量アクセスの負荷が心配である」
- **構造化された記述例**：「月末の利用集中時に複数ユーザーが同時に CSV 出力を実行した場合（原因）、API サーバーのメモリおよび DB 接続数が枯渇し（事象）、通常業務の画面表示までタイムアウトしてサービスが停止する恐れがある（影響）」

# リスク対応の5つの戦略

特定されたリスクに対しては、以下の 5 つの戦略から適用する手法を選択する。

| 戦略 | 内容 | 具体例 |
| :--- | :--- | :--- |
| **回避（Avoid）** | リスク要因となる仕様や技術の採用を取りやめる | セキュリティ要件の不確実性が高いため、初回リリースでは個人情報を含む項目を出力対象外とする |
| **軽減（Mitigate）** | 発生確率または影響度を事前に低減させる | タイムボックスを設けて負荷検証（スパイク）を行い、クエリのインデックスを事前に最適化する |
| **移転・分担（Transfer / Share）** | 外部のサービスや基盤を活用してリスクを分散する | 自前でファイル生成基盤を構築せず、クラウドのマネージドな非同期ジョブ基盤に処理を委譲する |
| **受容（Accept）** | 発生確率や対策コストを考慮し、リスクを許容したうえで安全弁を設ける | 現状の構成のままリリースするが、メモリ使用率のアラート監視を設定し、異常検知時のプロセス自動再起動と切り戻し手順を整備しておく |
| **エスカレーション（Escalate）** | チームの権限や技術的裁量を超えている場合、上位者へ判断を仰ぐ | 納期を延期するか、機能スコープを削減するかをプロダクトマネージャーに決定してもらう |

# CSV出力機能における適用例

- **不確実性**：10 万件以上の大量レコードに対する集計・出力処理時のサーバー負荷が未知数。
- **リスクの構造化**：月次締め日に大量ダウンロードが集中した場合、DB リソースが枯渇し、本番のトランザクション処理が遅延するリスクがある。
- **対応戦略の適用**：
  - **軽減**：同期的な HTTP レスポンスではなく、SQS を介したワーカープロセスによる非同期処理を採用する。
  - **回避**：出力期間の上限を「最大 3 ヶ月」に制限するバリデーションを導入し、想定外の巨大クエリの実行を防ぐ。
  - **受容と安全弁**：ワーカープロセスのメモリ上限を設定し、処理時間が 60 秒を超過した場合は安全にタイムアウトさせてエラーログを Slack へ通知する仕組みを実装する。
