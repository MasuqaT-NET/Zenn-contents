本章では、「不確実性・リスク・問題」の連鎖構造と、手戻り（もったいない）を未然に防ぐ段取りの要諦を整理する。

# 不確実性が問題となるまで

プロジェクトのトラブルは唐突に起きるのではなく、以下のプロセスを経て現実化する。

1. 不確実性
2. リスク
3. 事象
4. 問題

例えば、バイブコーディングの利用 → 技術的負債が増える恐れ → 変なコードが大量に取り込まれた → 機能改修が難しい 。

- **ダンドリの本質**: 「問題」がトラブルになってから対処するのではなく、手前の「リスク・不確実性」の段階で手を打ち、問題を未然に蒸発させることにある。

# タスクではなくリスクを管理する理由

- **氷山の一角（未知領域の存在）**: 目に見えるタスク（水面上）はごく一部。水面下の巨大な未知領域をどう取り扱うかが鍵。
- **リスクの数理的性質（足し算 vs 掛け算）**:
  - **タスクは「足し算（加算）」**: 個々の作業時間は足し算で積み上がり、正規分布（平均値付近）に収束しやすい。
  - **リスクは「掛け算（乗算）」**: リスクは工数を「1.2 倍」「1.5 倍」に膨らませる係数として作用する。掛け算が重なると、工数分布は対数正規分布になる。ロングテールであるし無限大もありえる。
- **発見の手法**:
  - マネージャー単独の認知には限界がある。多様な職種の集合知と、現場の「違和感に敏感な人（炭鉱のカナリア）」の直感を信じる。
  - 形式的な進捗報告よりも、日々の雑談・分報・心理的安全性こそが不穏なシグナルを早期に炙り出す。
- **リスクベースマネジメント（RBM）**:
  - リスクベーステスト（RBT）の思想をプロジェクト全体に拡張し、不安要素や影響度の大きいハイリスク領域から優先して着手・検証する。

# 不確実性の解剖

- **3 つの不確実性（『エンジニアリング組織論への招待』）**:
  - **目的不確実性（Why / What）**: 何を作るべきか、誰の課題か、市場や要求の曖昧さ。
  - **手段不確実性（How）**: どう作るか、技術的実現性や性能、アーキテクチャの不確実さ。
  - **通信不確実性（Who）**: ステークホルダー間の認識ズレ、前提の食い違い。
  - その他にも不確実性は定義できる。
- **「上流」は不確実性の塊**:
  - 上流工程は情報が最も少なく、不確実性が最も凝縮された領域である。上流での「1 のズレ」は下流へ進むにつれて掛け算で増幅し、リリース直前に「100 の手戻り」となって爆発する。上流の霧を晴らすことが最強のダンドリとなる。

# リスクとマネジメント

リスクがあるからこそプロジェクトマネジメントやダンドリが必要になる。

- **リスクの性質**:
  - 連鎖する（ドミノ倒し）、階層性を持つ（マトリョーシカ）、見えづらい（地雷）、立場により評価がブレる（万華鏡）。
- **リスクの構造化**:
  - リスクを「原因（ドライバー） → 事象 → 影響（損失）」で捉えることで、テコ入れすべき点が明確になる。ここを抑えることで良いダンドリができる。
- **リスクへの対処**:
  - **戦略**: 回避（原因排除）、軽減（確率・影響の抑制）、転嫁（外部移転）、受容（バッファ確保・BCP）、エスカレーション（上位判断）。
  - すべてのリスクをゼロにすることはできない。コントロール不能なリスクは受容し、コントロール可能なリスクに資源を集中する。
  - 認知下に置き続けることですべての不確実性に対してのダンドリが進む。

# 段階的詳細化で「もったいない」を削る

- **不確実性を削る具体的プラクティス**:
  - **目的**: プロトタイプ検証、完了の定義（DoD）・受け入れ基準の早期合意。
  - **手段**: スパイク、トレーサー弾。
  - **通信**: ユビキタス言語、ADR（意思決定記録）、オープンな非同期コミュニケーション。
- **段階的詳細化**:
  - 最初からすべてを決め打ちせず、近い未来は高解像度にタスク化し、遠い未来は粗い粒度にとどめる。情報が集まり霧が晴れるにつれて計画の精度を反復的に高める。
- **学習**:
  - あとからの振り返りやポストモーテムを通じて教訓を蓄積して今後に備える。
