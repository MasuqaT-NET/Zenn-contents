# プロジェクトマネジメントの概要

- **「プロジェクト」の本来の性質**
  - **有期性**: 明確な始まりと終わりがある
  - **独自性**: 過去と全く同一のものはなく、独自の成果物や目的を生み出す
- **ひとことで言えば**: **「目的を定め、計画を遂行して達成する」** こと
  - 単なるスケジュール管理やガントチャートの更新、進捗監視（マイクロマネジメント）ではない
  - 目的（Why / What）を明確にし、そこに到達するための道筋（How）を描き、現実の摩擦や状況変化に適応しながらゴールへ到達させる一連の営み
  - 開発現場で頻発する手戻りや待ち時間、認識齟齬を防ぎ、成果を確実に出すため必要な手法
- **歴史**
  - ちょうど [プロジェクト管理の歴史の概要](https://support.microsoft.com/ja-jp/project/history-of-project-management) や [プロジェクト管理の歴史年表：ピラミッドからアジャイルまで](https://ones.com/ja/blog/project-management-history-pyramids-agile-waterfall-gantt-chart-cpm/) という記事があったので、これを見ると良いだろう。

# プロジェクトマネジメントを構成する 5 つの領域

- **1. 立ち上げ**:
  - 何のためにこの取り組みを行うのか、何を達成すれば成功なのか（ゴール基準・成果物の定義）
  - 目的が曖昧な計画は、どれほど精緻にスケジュールを引いても途中で空中分解する
- **2. 計画**:
  - 目指すべきゴールと現状の間にあるギャップは何か
  - 何が最大の障害（ボトルネック・技術的制約・組織的課題）になっているかを客観的に見極める
  - 課題を克服するための基本方針（戦略）を立て、それを具体的なマイルストーンやタスク、リソース配分に落とし込む
  - 理想論ではなく、現実的な制約（時間、人員、予算、技術的負債）を踏まえたロードマップを描く
- **3. 実行**:
  - そのときの計画に基づいて業務を進める。次のモニタリングと一体的に動かす。
  - ステークホルダー（開発メンバー、ビジネス側、デザイン、外部連携先など）の間で情報と意思決定を滑らかに流す
- **4. モニタリング**:
  - 状況変化や新たな問題が発生した際に、柔軟に計画を再調整（軌道修正）しながら前進させる
  - 不確実性（技術的困難、要件変更、外部依存の遅延など）を洗い出し、発生確率や影響度を見積もり、先回りして予防策・軽減策（プロアクティブな手当て）を講じる
- **5. クローズ**:
  - 収束に向けた動きをする
  - 大事なことではあるが、今回の段取りの話としてはこの領域は省く（終わらせるためのダンドリはもちろん存在する）。 

# プロジェクトマネジメントの難しさ

- **1. 初めての内容・一点物（独自性）**
  - 定常業務（工場のライン生産や定例運用）との決定的な違い
  - 開発の「プロセス」（設計・実装・テスト・デプロイ）自体は繰り返されるものであっても、**開発で作る「対象・機能・要件・期待」は毎回新しい**
  - 作る対象だけでなく、チームの顔ぶれ、技術スタック、ユーザーの要求、市場状況も毎回異なるため、まったく同じプロジェクトは二度と存在しない
- **2. 成功の再現性の低さ**
  - 「前回のプロジェクトでうまくいったやり方」が、前提条件が少し変わるだけで全く通用しなくなる
  - 成功要因が「たまたま優秀な個人がいた」「外部環境に恵まれた」という幸運に左右されやすい
  - トレードオフの連続になる。マニュアル通りになぞれば必ず成功するような「銀の弾丸」は存在しない。
    - プロジェクトマネジメントのみで解決する際は、ゼロサム的なトレードオフ。
    - 新しい技術や革新をすれば、不満が無いようなトレードオフになることもある。こちらはプロジェクトマネジメント外。
- **3. 未知領域（不確実性・氷山の一角）を扱うこと**
  - プロジェクト開始時点で見えているもの（仕様書に書かれたタスク、要件）は「氷山の一角」に過ぎない
  - 水面下には、まだ言語化されていないステークホルダーの期待、隠れた依存関係、検知できていない問題といった巨大な「未知領域」が広がっている
  - プロジェクトマネジメントは、あらかじめ敷かれたレールの上を走る仕事ではなく、事件や災害（比喩）をも考慮して脱線を未然に防ぐ仕事だから、難しい

# 集中的に行うプロジェクトマネージャーという役割・専任者

- **専任プロジェクトマネージャー（PjM）の役割と機能**
  - 中間管理職的なバッファとして、各ステークホルダーの利害関係を調整し、現場が開発に集中できる環境を整える
  - 組織間（ビジネス部門 vs 開発部門）、役割間（PdM、デザイナー、エンジニア、QA）、専門領域間の「境界（サイロ）」に立ち、情報と意思決定を滑らかに流すハブ
- **専任者・特定個人に集中させるモデルの限界と弊害**
  - **ボトルネック化**: プロジェクトマネージャーの能力が業務のスピードや質の上限（制約）になってしまう
  - **当事者意識の喪失**: 受け身の姿勢を生み、現場のオーナーシップが失われる
- **本書が目指す姿: 特定個人への依存から「全員ダンドリ」へ**
  - 特定の「神マネージャー」に依存する組織ではなく、エンジニア一人ひとりが自らプロジェクトマネジメント（ダンドリ）を実践し、自律的に進められる組織へ
- **専任者を不要にする、あるいは、依存を減らすフィードバックの 3 つ次元**
  - **1. 小規模化**:
    - 業務のタスクの粒度をより小さく分割する
    - 1 回あたりの影響範囲と不確実性を小さくすることで、大掛かりな調整や専任の管理者を不要にする
    - 小さく学べ、学びの総量を増やせる
  - **2. 高頻度化**:
    - 月次や四半期ごとの重い報告ではなく、数時間単位で確認・共有・軌道修正のサイクルを回す
    - 問題が小さなうちに検知して潰すことで、致命的な手戻りや炎上を未然に防ぐ
    - 早く学べ、学びの総量を増やせる
  - **3. 分散化**:
    - プロジェクトマネージャーなどの単一のハブを経由せず、当事者同士が業務を進める
    - 全員が「目的・戦略・リスク」の共通認識を持つことで、現場での自律的な判断が可能になる
    - 全員で学べ、学びの総量を増やせる
